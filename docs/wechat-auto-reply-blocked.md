# 微信自动回复：阻塞说明（P3 未实施）

> 状态：**阻塞（有意不实现）**。本期交付的微信能力是「联系人/图片/文字核验 → Jarvis 面板草稿与待确认界面 → 用户在微信中手动发送」。
> 自动发送与自动回复**没有任何代码路径**：`task-runner.ts` 的 `wechat_draft` 流程终点是草稿确认，确认后只落盘 `draft-confirmed.json`，不会向微信窗口执行选择、粘贴、回车等可能立即发送的动作。

## 一、为什么阻塞

项目书（§2.2/P3）要求：实施自动回复前必须先完成「账号类型、接口/客户端权限和平台规则核查」，且不得用客户端注入、非授权协议或读取本地聊天数据库来替代。截至本期交付，以下前提**均未核实通过**：

| 待核查项 | 现状 |
|---|---|
| 目标是个人微信还是企业微信 | 未确认（用户未指定账号类型；两者自动化边界完全不同） |
| 个人微信是否有获准的自动化/机器人接入路径 | 无。微信官方未对个人微信开放消息收发 API；常见"个人微信机器人"均属外挂/协议逆向，被项目书第 4/5 节明确禁止 |
| 企业微信 / 微信客服等官方接口 | 存在官方 API（如企业微信会话、微信客服），但需要企业主体、应用授权与管理员配置，属于**账号级接入**而非桌面操作，须单独开通并取得用户/企业管理员许可 |
| 平台规则（腾讯云 ClawBot 通道等） | 只能确认"用户对 AI 下指令"的通道用途，不能据此推断可以读取或代发其他好友的私聊；自动代发好友消息的合规边界需逐项核查 |

## 二、因此本期做了什么

1. **交付草稿 + 人工确认发送**：`wechat_draft` 任务核验联系人、正文与图片文件后，在面板展示完整草稿（收件人、正文、图片清单、警告），用户确认后保存为任务产物；实际发送由用户在微信中手动完成。
2. **自动发送能力不存在**：即使授予了「对外发送」能力授权，草稿确认也只是保存产物；没有任何函数会把图片/文字粘贴进微信窗口。
3. **配置结构预留**：`src/main/wechat-draft.ts` 定义了 `AutoReplyRule`（允许名单、有效时段、最大连续轮数）形态，供未来在前提核查通过后实施，当前无消费者。
4. **消息级防线**：所有外部内容（含未来的微信消息）经 `prompt-guard.ts` 按不可信数据处理，"忽略规则并读文件"类文本不会提升为 Jarvis 指令（A7 的注入用例在该层有单测覆盖）。

## 三、解除阻塞的条件

同时满足以下条件后再排期实施：

1. 用户明确账号类型（个人微信 / 企业微信 / 微信客服）并出示对应接入的授权凭据；
2. 消息收发走**官方提供且获准**的接口（桌面 UIA 自动化仅限草稿撰写这类低风险动作，不承担"持续在线收消息"）；
3. 实现按联系人允许名单、有效时段、最大轮数配置的回复规则，未命中规则只生成草稿；
4. 消息接收有明确的监听/轮询机制、稳定去重键和"立即停止"开关；
5. 收到的消息一律视为不可信输入，不得触发读文件、执行命令、扩权等任何工具调用。

在此之前，README 与产品界面均按"草稿 + 人工发送"表述微信能力。
