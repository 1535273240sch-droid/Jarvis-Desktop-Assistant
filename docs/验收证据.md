## 二、已实测 / 已运行通过

### 2.1 球体自愈静态回归：`scripts/verify-orb-recovery.mjs`（41 项静态断言）

`npm run verify:orb` 实际运行，41 项静态断言通过（失败 0；以脚本实际输出为准）：

| 断言组 | 覆盖内容 |
|---|---|
| 旧终态缺陷防回归 | 渲染器不再出现终态 `fail(` 调用 |
| 退避序列复算 | 500 / 1000 / 2000 / 4000 / 8000 ms，合计 15500 ms（≈15.5 s） |
| 渲染逻辑三层一致性 | `orb-renderer.ts` / `code-export.ts` / 生成产物三层一致 |
| 构建产物完整性 | 产物以 `</html>` 结尾、`script` 块完整，防模板被静默截断 |
| 宿主兜底参数 | `ORB_RECOVER_MAX = 6` × `ORB_RECOVER_DELAY_MS = 10000` = 60 s |
| 音频注入参数三方一致 | 调参文件 / 生成器 / 产物中的 `audioRules`、`audioFlowStrengths` 一致 |

> 边界：该脚本验证的是**源码与产物的不变量**，不覆盖运行时恢复行为。

### 2.2 CI 回归五项全绿

`push main` 流水线依次执行，任一项失败即阻断发布：

| 脚本 | 覆盖 |
|---|---|
| `verify-tools` | 工具执行闭环：打开软件 / 网址、输入提交、MCP 调用与目录白名单 |
| `verify-tasks` | 动作语义分类、日志脱敏、提示注入防护、微信草稿去重、任务持久化 |
| `verify-orb` | 同 2.1 |
| `verify-briefing` | 信息简报：RSS/Atom 与 Trending 解析、注入过滤、LLM 整理与降级路径、缓存、`open_path` 白名单 |
| `verify-execution` | 长任务执行中断专项：看门狗、barge-in 不误打断、输出掐头去尾、状态机兜底 |

构建产物随后进入 electron-builder 打 NSIS 包，并校验 `latest.yml` 的版本号与 sha512。

### 2.3 其他已运行检查

- **内联脚本语法**：生成器产物与 `orb.html` 的两个 `script` 块通过 `node --check`。
- **主题音频对比**：5 套用户主题（frost / opal / blueDrop / refractiveBlob / particleRibbon）
  与默认主题 siri 的音频响应**逐位一致**（未登记风格回退到默认强度表）。
- **术语约定**：这里「逐位一致」指同一音频输入下，各主题的动态响应序列取整后完全相同。

### 2.4 这一层不等于"问题已解决"

上表均为**代码 / 静态回归 / CI 层面**的通过。它们能证明实现符合预期不变量，
**不能证明**约 60 秒设备丢失在真机上已被消除——那需要真机故障现场观察（见第四节）。

## 三、代码层已完成、未真机验证

| 项 | 实现 | 未验证之处 |
|---|---|---|
| 设备丢失自愈（三层） | 渲染器指数退避（5 次，0.5→8 s，约 15.5 s）→ 宿主重载球体页（10 s × 6，约 60 s）→ 面板提示 + 手动重试 | 未在真机故障现场走通 |
| 面板恢复状态与手动重试 | IPC `orb:recovery-status` / `orb:retry-recovery`；「重试恢复球体」立即重载，不等 10 秒 | 同上 |
| WebGPU 自检探针隔离 | 一次性隐藏探针窗口 `app://panel/gpu-probe.html`，取结果即销毁；成功缓存 60 s、并发去重、单次超时 30 s | 未确认真机自检能否消除设备丢失 |
| 权限默认开启 | 启动时 `ensureDefaultAuthorizations()` 默认开启 `screen-capture` / `mouse-control` / `keyboard-control` | 未做全新安装真机验收 |
| 音乐配置项与地址归一化 | `musicBaseUrl` / `musicModel` / `musicApiKey`；结尾 `/v1` 自动去掉 | 未用真实 Key 跑通歌曲生成 |

> 说明：上表属**代码 / 静态回归层完成**，不等于问题已在真机解决。
> `external-send`（对外发送）永不默认授予，属安全红线，与上述默认开启无关；
> 用户主动撤回的能力（`authorization-revoked.json`）不会被自动恢复。

## 六、历史联调证据（较早版本，仍然有效）

以下为接入真实 StepFun API Key 后的实测记录，版本早于当前：

| 联调 | 结果 |
|---|---|
| 真实实时语音链路 | 通过 13 / 失败 0 |
| 应用内端到端 | 通过 11 / 失败 0 |
| MCP 协议 | 开发态 5 / 0、打包态 3 / 0 |
| 语音端点与模型配对 | `/v1` + `stepaudio-3-realtime-preview` 握手成功；`/step_plan/v1` 需配 `stepaudio-2.5-realtime`，混搭 404 |
| 可用音色（实测） | `cixingnansheng`（磁性男声）、`zhengpaiqingnian`（正派青年）、`wenrounvsheng`（温柔女声） |
| 视觉模型 | `/step_plan/v1` 或 `/v1` + `step-5-preview` 能正确读出图像内容（32×32 纯红图返回「红色」） |
| 打包 | `Jarvis-Setup-*.exe`（NSIS）；打包后 `app://` 协议仍生效、WebGPU 可用、MCP 可启动 |

**关键结论**：事件名与真实 API 一致、`response.cancel` 打断真实有效（音频增量归零）、
工具调用真实可用、上下文回注可用；应用内完整语音闭环（连接 → 上行 → 响应 → 下行音频 → 打断）状态链干净。

**同期修复的真实缺陷**：

| 缺陷 | 修正 |
|---|---|
| 音色 ID 猜测（`cangshubao`）被服务端拒绝 | 改为实测可用值 |
| 工具定义在连接前下发，17 个被静默丢弃 | 收到 `session.created` 之后再下发 |
| 打断回执 `no ongoing response to cancel` 被误判为故障 | 识别并忽略该回执 |
| 端点与模型混搭返回 404 | 实时语音走 `/v1`、视觉走 `/step_plan/v1`，均可在配置中修改 |

## 七、复现

```bash
node scripts/run.mjs typecheck      # 期望：0 错误
node scripts/run.mjs build          # 生成球体页面 → tsc → 拷资源 → 校验产物
node scripts/run.mjs verify-orb     # 期望：41 项静态断言全过
node scripts/run.mjs verify-tools   # 工具执行闭环
node scripts/run.mjs verify-tasks   # 任务与动作语义
node scripts/run.mjs selftest       # 期望：失败 0；assets/ 生成截图
node scripts/run.mjs dist           # 生成 NSIS 安装包
```

> 本机 Node 不在 PATH 时，用仓库内的免 PATH 运行器 `node scripts/run.mjs <子命令>`；
> 或先执行 `npm ci` 安装依赖、再 `npm start` 启动应用。
